# 数据与持久化约束

本文档定义项目数据、配置、保存、迁移和备份的安全要求。数据相关改动必须优先保证兼容性和可恢复性。强制规则摘要见根目录 `AGENTS.md`。

## 1. 基本原则

- 不破坏已有项目文件和用户配置。
- 保留现有 JSON schema 与原子写入行为；确需变更时必须提供兼容和迁移方案。
- GUI 与 CLI 必须复用相同的项目管理和持久化入口。
- 保存失败不得留下半写入文件。
- 危险操作应先备份或提供明确恢复路径。
- 不得将真实用户数据、备份、日志或用户配置提交到仓库。

## 2. `Project` 模型语义

`Project` 既是 dataclass，也实现 mapping protocol：

- `__getitem__`
- `__setitem__`
- `__contains__`
- `__delitem__`

需要特别注意：

1. dataclass 字段不能被真正删除。
2. `del project[key]` 会把字段重置为 dataclass 默认值。
3. `__contains__` 基于 `hasattr`，字段重置后依然可能报告为“存在”。
4. 判断字段是否有效时应检查其值，不要只依赖 `key in project`。

修改该协议前必须检查 GUI、CLI、迁移和序列化代码的调用方式，并增加针对默认值及旧数据的测试。

## 3. 配置合并与兼容修复

`_deep_merge` 对列表采用整体替换，而不是逐项合并。因此，旧版配置中的列表不会自动获得新版默认列表新增的字段。

`default_bill_column_widths_data` 等按列保存的配置需要按名称对照 `_DEFAULT_CONFIGS` 进行修复。当前修复入口位于 `config_loader.load_app()`。

新增列级配置项时必须：

1. 更新默认配置；
2. 更新旧配置修复逻辑；
3. 验证已有用户配置不会丢失自定义值；
4. 验证新字段能获得合理默认值；
5. 添加旧版本配置样例测试。

不要把列表误认为可以由 `_deep_merge` 自动补齐。

## 4. 项目文件写入

项目写入必须复用现有 repository/project manager 能力和原子写入机制。禁止在 GUI、CLI 或临时功能中直接使用 `json.dump` 覆盖项目文件。

写入路径应保证：

- 临时文件与目标文件位于可安全替换的位置；
- 写入完成后再替换正式文件；
- 异常时不损坏上一份可用数据；
- 需要时触发现有备份策略；
- 并发写入遵守现有锁机制。

CLI 写入还必须先执行 GUI 单实例保护，详细要求见 `docs/cli.md`。

## 5. 备份与删除

删除、覆盖、迁移等高风险动作应遵守现有备份策略。新增此类操作时应明确：

- 何时创建备份；
- 备份失败后是否继续；
- 备份保留和清理策略；
- 如何检查备份有效性；
- 用户如何恢复。

CLI 的项目删除必须显式传入确认参数，并在删除前强制备份。GUI 新增同类操作时应提供等价安全级别。

## 6. 数据迁移

数据结构变更应尽量采用“读取时兼容、写入时规范化”的渐进方式。迁移至少需要考虑：

- 新字段的默认值；
- 缺失字段；
- 旧字段名或旧格式；
- 未知字段是否保留；
- 部分损坏数据的错误信息；
- 迁移前备份；
- 重复运行迁移是否安全；
- 迁移失败后的恢复方式。

迁移脚本应放在 `scripts/` 或明确的迁移模块中，不应隐藏在界面事件处理代码里。

## 7. 异步保存生命周期

`ProjectSaveBridge` 在后台执行项目保存。持有它的宿主 `QObject` 在销毁前必须调用 `close()`。

原因是后台线程可能在宿主销毁后继续发射信号，产生：

```text
RuntimeError: Signal source has been deleted
```

当前主窗口通过 `MainWindow._on_close` 关闭保存桥。新增独立窗口、页面宿主或保存桥实例时必须：

1. 明确所有权；
2. 在关闭路径调用 `close()`；
3. 验证尚未完成的保存如何处理；
4. 测试快速关闭和测试套件 teardown；
5. 避免后台线程在 QObject 销毁后发信号。

## 8. 运行时路径

运行时数据默认位于：

```text
%APPDATA%\ConstructionAccounting
```

支持以下覆盖方式：

- `CPA_DATA_DIR`
- `CPA_PROJECTS_DIR`
- `CPA_BACKUPS_DIR`
- `CPA_CONFIG_DIR`
- `CPA_LOG_LEVEL`

测试替代目录时必须尊重这些变量，避免污染开发者真实数据目录。

## 9. 禁止提交的数据

不得提交：

- `projects/` 中的用户项目；
- `backups/` 中的用户备份；
- `logs/`；
- `config/user_config.json`；
- 含真实业务信息的导出文件；
- 密钥、令牌和其他秘密；
- 为测试创建但未清理的运行时文件。

测试数据应使用匿名、最小化 fixture，并放在明确的测试目录中。

## 10. 数据改动验收清单

- [ ] 旧项目可以读取。
- [ ] 新字段具有默认值。
- [ ] 用户已有配置不会被无意覆盖。
- [ ] 保存后重新加载结果一致。
- [ ] 写入仍是原子的。
- [ ] 备份策略仍然生效。
- [ ] 失败场景不会损坏上一份数据。
- [ ] GUI 与 CLI 的行为和计算口径一致。
- [ ] 环境变量指定的临时目录能够正常工作。
- [ ] 已增加迁移、兼容或回归测试。
